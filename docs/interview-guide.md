# FinLedger 面试与简历讲解

## 一分钟项目介绍

FinLedger 是一个基于 Java 17 和 Spring Boot 3 的模块化单体资金账户系统，模拟账户、充值、
转账和流水。项目重点是资金一致性：我用 MySQL 本地事务保证扣款、入账、订单和双边流水
原子提交；用 `SELECT ... FOR UPDATE` 防止并发超扣，并按账户 ID 固定加锁顺序降低死锁；
用数据库唯一约束和请求摘要实现 `Idempotency-Key`。Redis 只承担可降级限流，余额始终以
MySQL 为准。测试使用 Testcontainers 在真实 MySQL 上验证回滚、并发和幂等。AI 助手只做
受控交易查询，模型不能执行 SQL 或修改资金。

## 高频问题与回答要点

### 1. 为什么只加 `@Transactional` 还不够防止超扣？

事务保证一组操作原子提交，但普通隔离级别下两个事务仍可能先后读到同一个旧余额，各自都
认为余额足够。必须把读取与并发控制结合：本项目在事务内用 `SELECT ... FOR UPDATE` 锁定
账户，再基于锁定后的最新余额校验和更新。

### 2. A 扣款成功、B 入账失败怎么办？

扣款、入账、订单、两条流水和幂等记录位于同一事务，任一步抛异常都会整体回滚。不能捕获
异常后吞掉，也不能把这些步骤放到互不相关的事务中。集成测试会制造流水插入失败，直接查询
数据库确认所有写入均回滚。

### 3. 悲观锁和乐观锁怎么选？

悲观锁先锁后改，冲突请求等待，适合转账这种短事务、冲突敏感且失败代价较高的操作；缺点是
锁等待与死锁。乐观锁用 version 条件更新，不阻塞读取，适合低冲突场景；更新 0 行后需要重新
读取、重新校验和有界重试，高冲突时可能形成重试风暴。FinLedger 主路径使用悲观锁，同时保留
乐观锁 SQL 作为替代方案演示。

### 4. 为什么固定加锁顺序？是否完全消除死锁？

A→B 若先锁 A，B→A 若先锁 B，双方可能互等。统一先锁较小账户 ID，再锁较大 ID，可以消除
这条典型循环等待路径。但其他表、索引或不同代码路径仍可能形成死锁，因此生产系统还要捕获
数据库死锁并在幂等保护下对完整事务做少量重试。

### 5. 为什么金额不能用 `double`？

`double` 按二进制浮点表示，0.1 等常见十进制数不能精确存储，累加和比较会积累误差。
Java 使用 `BigDecimal` 并明确两位小数，MySQL 使用定点 `DECIMAL(19,2)`；比较金额用
`compareTo`，不要用 `equals` 判断数值相等，因为 `equals` 还比较 scale。

### 6. 幂等为什么不能只做“先查后转账”？

两个并发请求可能都在查询时看到不存在，然后都执行。FinLedger 先插入带唯一约束的占位记录，
让 MySQL 决定唯一执行者。后来的请求等待或得到 duplicate key，然后读取第一次成功响应。
请求摘要还能发现同一个 key 被配上不同账户或金额，返回冲突而不是误回放。

### 7. 幂等记录为什么和转账在同一事务？

如果占位先单独提交，业务失败后可能永久留下 PROCESSING；如果业务成功但结果记录失败，重试
又可能再次转账。同一事务让“获得执行权、资金变更、成功结果”共同提交或回滚。

### 8. 为什么余额和流水都要保存？

余额是当前状态，读取快；流水是状态变化的事实，支持审计、历史展示和对账。只存流水会让每次
余额查询都聚合大量数据；只存余额无法解释变化来源。二者必须在同一事务更新，并可通过流水
重算结果核对余额。

### 9. Redis 在项目中做什么？为什么不存余额？

Redis 用 Lua 原子执行固定窗口限流，故障时 fail-open，不参与转账事务。缓存存在过期、淘汰、
故障切换以及与 MySQL 双写一致性问题，因此不能成为余额或幂等结果的唯一事实源。

### 10. 如何证明事务和并发逻辑真的有效？

Mockito 只能验证分支与交互，不能证明 InnoDB 行锁和回滚。项目用 Testcontainers 启动真实
MySQL 8：两个线程通过闩锁同时从 100 元账户各转 80 元，断言只成功一次；还通过数据库触发器
让流水写入失败，断言余额、订单、流水和幂等记录都回滚。

### 11. JWT 权限如何避免水平越权？

用户 ID 只从 Spring Security 验证过的 JWT `sub` 获取，不接受 `X-User-Id` 或请求体 userId。
Service 查询账户和流水时继续带用户归属条件。认证证明“你是谁”，资源所有权校验证明“你能否
访问这条数据”，两层不能混为一谈。

### 12. AI 为什么不直接生成 SQL？

自然语言和模型输出都不可信。模型只生成固定意图、期间、条数和阈值，Java 再校验，随后调用
预定义且绑定 JWT userId 的 Mapper 查询。模型只收到授权后的结构化结果进行解释，没有数据库
凭证和写操作工具，因此提示注入不能直接变成资金操作。

## 代码讲解路线

面试现场可以按以下顺序打开代码：

1. `V1__create_core_tables.sql`：解释金额、约束、流水和幂等唯一键；
2. `IdempotentTransferService`：展示限流、摘要和重复请求分流；
3. `IdempotentTransferExecutor`：指出最外层事务边界；
4. `AccountService.lockTransferAccounts`：展示固定锁顺序；
5. `TransferService`：展示校验、双账户更新、订单和双边流水；
6. `FinancialFlowIntegrationTest`：用真实数据库测试证明设计；
7. `AiTransactionAssistantService`：解释 LLM 与核心系统之间的安全边界。

不要只背注解作用。重点说明每个设计在防止什么具体失败，以及测试如何证明它。

## 可写入简历的表述

以下内容已经有代码和测试支撑，可以按实际求职语言精简：

- 基于 Java 17、Spring Boot 3、MyBatis-Plus 和 MySQL 8 设计模块化单体资金账户平台，完成
  用户、账户、充值、转账、流水和 JWT 权限体系；
- 使用 Spring 事务和 InnoDB 行锁实现双账户原子转账，按账户 ID 固定加锁顺序降低反向转账
  死锁风险，并通过双线程 Testcontainers 用例验证无并发超扣；
- 基于 `Idempotency-Key`、SHA-256 请求摘要和 MySQL 联合唯一约束实现并发幂等，支持成功响应
  回放与 key 参数冲突检测；
- 设计余额快照与双边不可变流水，在数据库约束和异常注入测试下验证订单、流水与余额一致回滚；
- 使用 Redis Lua 实现按用户转账限流，明确 MySQL 为核心事实源，并实现 Redis 故障降级策略；
- 构建只读 AI 交易分析流水线，以严格结构化意图、Java 参数校验、JWT 数据隔离和预定义 SQL
  防止模型越权或直接操作资金。

不应声称：连接真实银行、支持真实支付清算、达到生产金融合规、彻底消除死锁，或外部模型已经
在无 API key 的环境中完成线上调用。
