# 转账幂等设计

## 目标

客户端超时后可以安全重试。对于同一用户、同一业务类型和同一
`Idempotency-Key`，系统最多执行一次真实转账。

## 执行顺序

1. 将转账参数规范化，并计算 SHA-256 请求摘要。
2. 在 `idempotency_record` 插入状态为 `PROCESSING` 的 claim。
3. 执行账户加锁、扣款、入账、订单和双边流水写入。
4. 将 claim 更新为 `SUCCESS`，保存资源 ID 和响应快照。
5. 上述步骤使用同一个 MySQL 事务提交或回滚。

唯一约束 `(user_id, business_type, idempotency_key)` 是并发竞争的最终裁判。
重复插入会等待首个事务结束：首个事务成功时，后续请求读取并返回已提交的响应；
首个事务失败时，claim 会随业务回滚，重试可以重新执行。

## 为什么不只使用 Redis

Redis 可以做前置去重或减轻数据库压力，但缓存过期、淘汰、故障切换和数据库事务
无法天然保持原子一致。资金业务的最终幂等事实保存在 MySQL，Redis 不能替代数据库
唯一约束。

## 请求摘要

摘要包含来源账户、目标账户和规范化为两位小数的金额。相同 key 搭配不同摘要返回
HTTP 409，避免误把另一个业务请求当成重试。
